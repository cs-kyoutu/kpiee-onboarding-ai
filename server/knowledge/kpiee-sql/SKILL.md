# kpiee 構築SQLの組み立て

## 1. このスキルの範囲

対象は「顧客の取込済み生データ（アセット）を、レポートに載せる集計データへ変換するSQL」を書く作業。
kpiee の SQLジョブに貼り付けて実行される SELECT 文が成果物。

**インプットはオンボーディングAIの「データ構造分析レポート」HTML原本の添付。**
必要なものはそこから読み、足りない機械的な情報（ワークスペースID・アセット一覧・
物理カラム名）は kpiee Redash から自分で取る。ユーザーに手入力させない。
詳細は `references/report-input.md` と `references/physical-columns.md`。

対象外：kpiee 製品自体の実装・設計（それは kpiee-designs / dx-kpiee 側の話）、レポート定義そのもの、
オンボーディング自動化AI（別プロダクト）の実装。

## 2. 前提となるデータ構成

```
顧客ファイル（CSV/Excel）
  → 取込 = アセット（例「2-1. [raw_広告費/ポイント] Amazon」）
      → Snowflake 物理テーブル  IMPORT_<アセットID>
        物理カラム  IMPORT_<アセットID>_<型>_<連番>
  → SQLジョブ（このスキルで書くSELECT）
      → 集計データ（表形式データ）
        → レポート（月次ロールアップ・マスタ階層はレポート側が担当）
```

物理カラム名の読み方（例：`IMPORT_30015_BIGINT_13`）

| 部分 | 意味 |
|---|---|
| `30015` | データファイルID（全社通し番号）。テーブル名は `IMPORT_30015`。**クエリ147が返す「アセットID」はワークスペース内の連番で別物**（協和の①はアセットID 23 ／ テーブル `IMPORT_30014`）。テーブル名は物理カラム名から読む |
| `BIGINT` | 取込時に推定された型。**業務上の型とは一致しないことが多い**（§4-2） |
| `13` | 取込元ファイルの列順。列を挿入されると番号がずれる |

物理カラム名は人間には読めないので、CTE の中で必ず業務名の別名に置き換えてから使う。

**別名は場所で使い分ける。**

| どこ | 別名 | 理由 |
|---|---|---|
| 中間CTE | **ASCII の snake_case** | 数が多く、壊れた箇所を特定しにくい |
| **最終SELECT** | **日本語（帳票の見出し）** | この別名が kpiee のカラムラベル（論理名）になり、**レポート指標の選択肢と、顧客が開く「数値の明細表示」の列見出しにそのまま出る** |

最終SELECTを日本語にする根拠は、顧客の画面に出るから。協和の [加工]AMEX手数料計算 で
`AS "手数料金額"` と書いた別名が、レポート定義の「カラム名」ドロップダウンに
そのまま出ているのを実物で確認した。ASCII のままだと `sga_after_alloc` が顧客に見える。

**VDI 経由のコピーでダブルクォートが壊れ `unexpected '集計'` になる実例がある**（協和で実測）。
ただし**壊れると必ず構文エラーになり、黙って間違った結果を出すことはない。**
だから最終SELECTは1か所にまとめ、壊れたらそのブロックだけ貼り直す。
**登録後にカラムラベルを手で直す運用にしない** —— 製品側で `column_label` は変更できるが、
直し忘れが**無症状**で顧客画面に残り、どこまで直したかの記録も残らない。

なお `'不明'` 処理や `= 'ZDA'` の比較で日本語・全角リテラルは避けられない。
別名だけ ASCII にしても、マルチバイトはSQLから消えない。

物理名（`DC_SQL_JOB_0028_DATE_C1`）は別に決まる。**参照経路が2つある** ——
レポート定義は論理名（＝最終SELECTの別名）で選ぶが、
SQLジョブが**別のジョブの出力を FROM で参照する**ときは物理名でしか書けない
（`references/physical-columns.md` §6）。

だから**渡すSQLには出力仕様（順番 → 別名 → 予測物理名 → 原本の列 → 下流での用途）を必ず添える。**
別名しか書かれていないSQLは、下流から見ると参照名が1つも分からない状態になる。

**明細は2種類ある。** 出力仕様（列名の対応。次の担当者向け）と、
計算明細（金額の導出過程。顧客・検算者向け）。**両方出す。片方で代用しない。**
さらに製品側にレポートのセル右クリック →「数値の明細表示」があり、
**そこに何が出るかは自分が決める出力列で決まる** — 中間値を落とすと顧客が明細を開いても
最終値1列しか出ない。3つの関係は `references/calc-spec.md`。

**「原本の列」（シート名・列記号・見出し）を必ず1列持つ。** 最終SELECTの別名を帳票の見出しに
合わせても、**どのシートの何列目か**は別情報で、物理名は記号のまま。
これが無いと顧客帳票のどの列に当たるか照合できるのは書いた本人だけになる。
**見出しは145の論理名から取る**（物理名と同じで人に聞かない・手で写さない）。
145に無いシート名・列記号だけを付録から補う。埋まらない列は `—`。見出しを創作しない。
型は `references/physical-columns.md` §8-0、連番・型トークンの予測は §8-1・§8-2。

## 3. 作業フロー

**着手したら `references/workflow.md` を開く。** 各ターンで何を出すか、何を聞くか、
どの順で検証するかはそこが正。記憶で進めない。骨格だけ再掲すると：

```
[ターン1] 取得ログ ＋ 復唱 ＋ 突き合わせ表          ← SQLは書かない
[ターン2] ロジックの復唱（付録の数式が根拠・根拠なし列も明示）＋ 類型の判定 ＋ 質問（1回で）
[ターン3] 事前検証クエリ（番号付き）＋ SQL（1区分）＋ 事後検算 をセットで
[ターン4] 検算の突き合わせ → 次の区分へ（3-4を繰り返す）
[最終]   統合SQL ＋ 最終検算 ＋ 出力仕様 ＋ 計算明細 ＋ 案件メモ
```

先立って、会話に案件メモ（`references/case-memo-template.md` の形）が貼られていれば、
アセットID・掛け目・マッピング表はそこを一次情報にし、同じことを聞き直さない。

## 4. 必ず守るルール

### 4-1. SQLジョブの契約（違反すると実行前に弾かれる）

- 文は **1本の SELECT または WITH のみ**。セミコロン区切りの複数文は不可。
- `INSERT/UPDATE/DELETE/MERGE/CREATE/DROP/ALTER/TRUNCATE/USE` は不可。
- `@stage` 参照は不可。
- `schema.func()` のような修飾付き関数呼び出しは不可。
- `CURRENT_USER` `CURRENT_ROLE` `CURRENT_SCHEMA` `SYSTEM$...` 等のコンテキスト/メタデータ関数は
  括弧あり・括弧なしのどちらの形でも不可。
- `FROM`/`JOIN` で参照できるのは登録済みアセット（同一スキーマ）だけ。

（一覧の根拠は `atlas-core/rails/app/services/sql_jobs/query_scanner.rb`。全リストは `references/validation.md`）

### 4-2. 物理カラムの型を信用しない

取込時の型推定はズレる。実例：`広告費` が `BIGINT_13` なのに中身は `"1,234"` の文字列、
`クリック` が `DOUBLE_10` で `CTR` が `BIGINT_11`（実際は率＝小数）。

- 数値として使う前に必ず「不要文字を削る → 数値化」を通す。
- **金額は `TRY_TO_DECIMAL(x, 18, 2)`、率・構成比は `TRY_TO_DECIMAL(x, 12, 6)`。**
  `TRY_TO_NUMBER` は既定 scale=0 で、**小数が黙って切り捨てられる**。
  按分比率を通すと全部 0 に潰れ、配賦額が丸ごと消える。エラーは出ない。
- 日付は `DATE` 型カラムならそのまま、文字列なら **書式を明示**して
  `TRY_TO_DATE(x, 'YYYY/MM/DD')`。**1引数版は使わない** — SQLジョブのセッションは
  `DATE_INPUT_FORMAT` が `AUTO` ではなく、`2026/05/01` のような素直な値でも NULL を返す（実測）。
  同じ列に複数書式（`YYYYMM`・Excelシリアル値）が混ざることもある。
- `TRY_` は1行の異常値でジョブ全体を落とさないために使う。
  ただし失敗が NULL に化けて静かに消えるので、**変換できなかった行を数えるクエリを併走させる**。

### 4-3. 空白は「不明」に寄せる

分類キー（商品グループ、部門など）が空のとき、集計から消えたり NULL 行が混ざるのを防ぐため
既定で `'不明'` を入れる。**`COALESCE` だけでは空文字を拾えない**：

```sql
-- NG: NULL しか拾えない。'' や ' ' や全角スペースは素通り
COALESCE(product_group, '不明')

-- OK: 空文字・半角/全角スペースだけの値も「不明」に寄せる
COALESCE(NULLIF(TRIM(product_group, ' 　'), ''), '不明')
```

`CASE ... ELSE '不明'` を書いたときは、**何が不明に落ちたかを必ず数える**
（`references/workflow.md` ターン3-a の全列挙クエリ）。
不明が想定より多ければマッピング漏れ。

金額を足し合わせる式では `COALESCE(..., 0)` を落とさない。**項に1つ NULL があると結果が丸ごと NULL**
になる（協和①は備品列の69%が空欄だった）。

### 4-4. マスタ突合が未確定なら、暫定であることを構造に残す

商品マスタ等の突合ルールが未決なら、突合キー（商品コード等）を列として保持したまま
分類列は `'不明'` を入れ、コメントで暫定と明記する。列を落とすと後から突合できない。

```sql
IMPORT_30002_STRING_10 AS product_code,   -- マスタ突合用に保持
'不明'                 AS product_group,  -- 商品マスタ突合が未確定のため暫定
```

## 5. SQLを書く前に確認すること

税込/税抜・掛け目・端数・対象期間・粒度・重複時の扱い・分類の出所・`'不明'` の入れどころ・
区分の分岐条件。レポートに書かれていなければ、書き始める前に**まとめて1回で**聞く
（後から全区分を直すのは高コスト）。項目の全リストは `references/workflow.md` ターン2-c。

## 6. 回答の作り方

- **単位はまとめて渡す。** 「A8の部分だけフルで」と言われたら、そのCTEを
  そのまま貼れる完成形で出す。差分（「ここの `ELSE ''` を `ELSE '不明'` に」）だけを返さない。
  差分指示は貼り替えミスとCTEのカンマ落ちを生む。
- **1回答＝1区分（1工程）** を基本にし、全部そろってから統合クエリを出す。
- **SQLと検算クエリはセットで出す。** ユーザーが実行担当なので、検算を次のターンに回すと
  往復が倍になる。SQLジョブは1文しか通らないので、**番号を振って1本ずつ**渡す。
- SQL内のコメントは日本語で、業務上の根拠（掛け目の理由、暫定である旨）を書く。
  構文の説明は書かない。
- **別名は中間CTEが ASCII、最終SELECTが日本語**（§2）。最終SELECTは1か所にまとめ、
  「ここが `unexpected …` で落ちたらこのブロックだけ貼り直してください」と添える。
  実行を依頼する検証クエリは、コピーが難しい環境を想定して
  列を絞る・`LIMIT` を付けるなど**スクショで足りる形**にする。
- 変更点は本文で1〜2行だけ説明する。SQLを再掲するときは省略記号で切らず全文出す。
- 未確定事項が残っているときは、出せるSQLを出したうえで最後に質問を添える。
  質問で止めない。
- エラー報告を受けたら原因を推測で1つに決めず、実行したSQL全文とエラー原文をもらう。
