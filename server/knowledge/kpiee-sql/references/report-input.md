# インプット：オンボーディングAIのデータ構造分析レポート

このプロジェクトの一次情報は、オンボーディングAIが出力する
`<顧客名>_データ構造分析レポート_<日付>_生成版.html`。

## 1. 必ず HTML 原本を添付してもらう

テキストに変換したもの、ブラウザから全選択コピーしたものは受け取らない。

理由は `<details>` の折りたたみ。レポートには
「**付録を開く**（全N ファイルの列構成・数式根拠）」「表と列の構成を開く」「関係の一覧を開く」
が十数か所あり、**列構成と数式 lineage はその中に入っている。**
折りたたまれた中身はコピーに含まれない一方、HTMLソースには全部残っている。

添付が大きい（150〜480KB。実体の8割以上はCSS・JS・座標値）ため、
全量ではなくチャンク検索で読まれることがある。**だから §3 の復唱を必ず先に行う。**
付録が静かに欠けたまま SQL を書くのが、この設計で唯一の重大な事故。

## 2. どこに何が書いてあるか

| 見出し | 中身 | SQLでの使いどころ |
|---|---|---|
| `01 受領データ一覧` → ファイルごとの役割 | 元データ／マスタ／中間／最終 の分類、行数 | どれが土台でどれが突合先か |
| `02 再現するアウトプットの確認` | 最終アウトプットのファイル・シート・グレイン | 出力の形。**ここが SELECT の最終形** |
| `03 ロジックの確認` | ファイル間の関係図、最終アウトプットの列ごとの作られ方 | JOIN の骨格と計算式 |
| `付録`（`<details>`） | **全ファイルの列構成 ＋ Excel数式の原文** | 列の対応表と計算式の根拠 |
| `05 今後の進め方` | 未確定事項（03-A/B/C、Q-01〜） | 質問リストの出発点。勝手に埋めない |

付録の数式は `IFERROR(VLOOKUP($D6, SPD収支管理表!$A$2:$J$90, 6, 0), 0)` のような原文で載る。
「どの列が・どの表を・どのキーで・何列目を引くか」がそのまま JOIN 定義になる。

## 3. レポートには無いもの（勝手に補わない）

- **実データの値。** レポートは「数値そのものは含まない」と明記されている。
  `¥` ・カンマ・全角スペースの有無はレポートからは分からない
  → 型トークンと実データで判断する（`physical-columns.md` §5）
- **物理カラム名。** kpiee が取込時に生成するのでレポートには存在しない
  → Redash から自動取得する（`physical-columns.md`）
- **ワークスペースID。** 顧客マスタから引く。空のときだけユーザーに聞く
- **検算の正解値。** レポートは実データの値を含まず、原本も見られないので自分では作れない。
  ユーザーが顧客帳票／kpiee画面から拾って渡す前提（`reconciliation.md` §0）
- **付録に載らなかった表。** 「23表中8表のみ掲載」のような欠落が起きる。
  復唱で件数を出して、欠落を先に可視化する

## 4. レポートと実物がズレることがある

協和医科器械での実測（原本zipと突き合わせた結果）:

| # | レポートの記載 | 実物 |
|---|---|---|
| 1 | `⑨拠点別経費.csv` | `⑥拠点別経費.csv`（⑥が2つある） |
| 2 | ①は `.xlsx` | `.xlsm`（マクロ付き） |
| 3 | ファイル10点 | 11点（顧客が書いた手順書txtが追加） |
| 4 | 「縦: エリアフラグ・エリア…」を列名として記載 | 実際はA列の**値**（フラグ4種） |

さらに **期ズレ** があった。最終アウトプット★は67期、土台①は68期集計。
検算の基準をどちらに置くかで結果が変わるので、期が揃っているかは必ず確認する。

ズレの検出はレポート内の突き合わせ（`01 受領データ一覧` の件数 vs 付録の表数）と、
Redash から取った実際のアセット・列構成との照合で行う。`physical-columns.md` §4。

## 5. 原本 Excel は見られない前提で組み立てる

**顧客の原本ファイルの添付を求めない。** 使える根拠はこのレポートまで。
その中でも `03 ロジックの確認` は要約なので SQL の根拠にはならず、
**根拠になるのは付録（`<details>`）に載った Excel 数式の原文だけ。**

### 5-1. 付録の数式は「代表1セル分」しかない

これが今の設計で一番効く制約。付録は列ごとの網羅ではないので、
最終アウトプットの列の多くは数式が載らない。協和の
`★顧客別営業利益試算ver5.xlsx` はメイン39列に対し、レポートに残った数式が9件だった。

だから **列を3つに仕分けて、件数ごとユーザーに提示する**（ターン2-a）:

| 区分 | 扱い |
|---|---|
| 付録に数式がある | 原文を引用して「1指標＝1行」に展開 |
| 付録に数式が無い | **根拠なし。** SQLに書かず、プレースホルダ＋コメントで残す |
| 数式が存在しない列（手入力・手作業転記） | 手入力であることを明示（協和は42組、Q-02 として顧客確認へ） |

**「レポートに書いてあるからOK」と判断しない。** 逆に、
埋まっていない列を埋まっているように見せない。

### 5-2. 数式原文があっても落としやすい3つ

読み飛ばすと**エラーが出ないまま数字が狂う**:

| 落とすもの | 数式ではどう書かれているか |
|---|---|
| 金額の**出所シート** | `VLOOKUP(D6, 拠点別経費!...)` — どのシートを引いているか |
| 合計の**項の数** | `Z = SUMIFS(S)+SUMIFS(T)+SUMIFS(U)+SUMIFS(X)` — 4項ある |
| 分母の**母集合条件** | `SUMIFS(L:L, B:B, B, L:L, ">0")` — 正のものだけ |

協和では、レポートの要約だけを根拠に書いた STEP4 の SQL に**この3つが揃って入っていた**。
当時は原本の数式を直接読んで `O = L + R` から `営業利益 = P − AC` まで
列単位で書き起こし、それで全部出た。**今はその退路が無い。**
付録に原文があるなら1文字ずつ読む。無いなら「不明」と書く。

### 5-3. 埋まらないときの選択肢（ユーザーに丸投げしない）

不明な項目をそのまま質問に流さない。原本を見ないかぎりユーザーも答えられないので、
聞いても問題を移すだけになる。出すのは次の3択:

- **(a) レポートの再生成** — オンボーディングAI側で数式 lineage を増やして出し直す。
  根拠なし列が多いときの根本策はこれ。カバー率（例「39列中9件」）を添えて提案する
- **(b) 未確定のまま進める** — 根拠なし列をプレースホルダで構造に残し、
  後から1か所直せば済む形にする。SQL は出す。質問で止めない
- **(c) 数値からの逆算** — その列の**あるべき数値**をユーザーに確認してもらい、
  式を当てにいく。ユーザーが顧客帳票や kpiee 画面から拾える範囲でだけ成立する

(c) は検算の正解値を取る動きと同じなので、ターン2の質問でまとめて頼む
（`reconciliation.md` §0）。
