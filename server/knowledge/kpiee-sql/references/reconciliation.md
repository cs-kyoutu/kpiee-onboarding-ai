# 検算 — SQLと必ずセットで出す

SQLを渡すときは検算クエリを**必ず同伴させる**。ユーザーが実行する運用なので、
検算を別ターンに回すと往復が倍になる。

SQLジョブは1文しか受け付けないので、**検算も1本のSELECTにまとめる**か、
「これを順に流してください」と番号を振って分けて渡す。

## 0. 検算の正解値はユーザーから受け取る（自分では作れない）

**原本 Excel は見られない前提**なので、正解値を自分で算出する手段が無い。
レポートも実データの値を含まない。だから正解値は
**ユーザーが顧客帳票か kpiee 画面から拾って渡すしかない。**

**ターン2の質問にまとめて含める。** ターン4になってから「正解は何ですか」と聞かない
（そのタイミングだと往復が1回増える）。頼み方は具体的に:

```
検算のために、次の数値を顧客帳票から拾って教えてください。
  ・区分（工程）ごとの合計 — 売上／粗利／経費
  ・対象の期と期間（何期の何月〜何月か）
  ・その数値が載っているシート名（後で食い違ったとき切り分けに使う）
```

参考までに、協和では原本が読めた時期に次の基準値を自分で作っていた。
**今はこの形の数値をユーザーからもらう**、と考えればよい:

```
①68期集計得意先別実績
  行数            3,991
  売上(備品)      12,865,218,722   （数字がある行 1,232 — 残り69%は空欄）
  粗利(備品)       1,435,267,090
  売上(備品外)    86,850,544,750   （3,962行）
  粗利(備品外)     7,741,207,712
```

**期がズレていないかを先に確認する。** 協和は最終アウトプット★が67期、土台①が68期だった。
違う期の数字と突き合わせると、永遠に合わない。だから期と期間も併せてもらう。

**正解値が来ていない項目は「未検証」と明記する。** 事前検証が通っただけで
「合っている」と書かない。検証できていないことを黙って飲み込むのが一番危ない。

## 0-b. 本体を流す前に「前提を壊す検証」を先に出す

検算には2種類あって、**順番が違う**。

| 種類 | いつ | 何を見るか |
|---|---|---|
| **事前検証** | 本体SQLを1度も流す前 | 書いたSQLの**前提**が実データで成立しているか |
| 事後検算 | 本体を流した後 | 出た数字がユーザーから受け取った正解値と合うか |

事前検証を飛ばすと、本体が**エラーを出さずに壊れる**。協和で実際にそうなった:
`TRY_TO_DATE(x)` の1引数版が NULL を返し、AMEX の実績が全消えする状態で本体を書いていた
（`cleansing-recipes.md` §1）。

事前検証の型（協和で実際に流した5本。**この順序**）:

```
0  変換の成否      日付・金額の生値 × 変換結果 × 件数を GROUP BY。NULL 化していないか
1  前提の成否      「部門コード = 拠点」のような、SQLが黙って置いている前提の反証を取る
2  キーの一意性    1キーに突合先が複数ないか（あれば代表選定ルールの合意が要る）
3  未マッチ金額    マスタに無くて分類が付かないキーと、その金額（§3）
4  残余マイナス    引き算の結果が負になる行（§2）
```

**SQLジョブは1文しか通らないので、番号を振って1本ずつ渡す。**
0 が落ちたら 1 以降は流させない。前提が崩れた状態の結果を見ても意味がない。

## 1. 合計保存（配賦の検算・最重要）

```
配賦元の総額 = 配賦先に配られた合計 ( + 配賦元に残した分 )
```

月ごとに出す。1円単位で合わせる必要はないが、**桁が違う差は必ず追う**。

```sql
SELECT
    month,
    SUM(source_amount)                          AS src_total,
    SUM(allocated_amount)                       AS dst_total,
    SUM(source_amount) - SUM(allocated_amount)  AS diff
FROM ...
GROUP BY 1 ORDER BY 1
```

| 差の大きさ | 判定 |
|---|---|
| 数円〜数十円 | 端数。合格（協和の実測は売上2円・粗利5円） |
| 特定の月だけ大きい | その月の分母が0か、基準データが欠損 |
| 全月で一定割合ずれる | 比率の分母が違う（`allocation-sql-skeleton.md` §2） |
| 配賦先の方が多い | **二重計上**。同じ元金額を2つの工程が配っている |

## 2. 残余がマイナスになっていないか

隠さずに件数で出す。0に丸めて進めない。

```sql
SELECT COUNT(*) AS negative_rows, MIN(residual_amount) AS worst
FROM residual WHERE residual_amount < 0
```

1件でも出たら、既配賦が総額を超えている＝どこかで重複している。

### 「配り残し」は異常とは限らない

残余がプラスのまま配賦されずに残ることがある。**これは原本ロジック上の正常な結果でありうる。**
協和では 2.36億（残余の約4%）が未配賦で残ったが、内訳は**得意先が1件も紐づかない本部部門**
（営業推進部1.69億・管理部4,857万ほか）だった。配賦先が存在しないので配りようがない。

やること: **未配賦を0にしようとする前に、内訳を出して正常か異常かを判定する。**

```sql
SELECT base_key, base_name, residual_amount, dst_count
FROM residual WHERE dst_count = 0 ORDER BY residual_amount DESC
```

`dst_count = 0`（配賦先ゼロ）なら正常。配賦先があるのに配られていないなら比率の不具合。
どちらであっても**金額と件数を報告する**。黙って残すのと、説明して残すのは別物。

## 3. 未マッチで消えた金額

`INNER JOIN` や `CASE ... ELSE` で静かに落ちた金額を数える。**エラーにならないので見えない。**

```sql
SELECT
    COUNT(*)                                              AS unmatched_rows,
    SUM(amount)                                           AS unmatched_amount,
    COUNT(DISTINCT join_key)                              AS unmatched_keys
FROM base b
LEFT JOIN master m USING (join_key)
WHERE m.join_key IS NULL
```

`'不明'` に落ちたものも同じく件数と金額を出す。
**マッピングは実データの全列挙を覆っているか**をここで確認する。

## 4. 数値化に失敗した行

`TRY_TO_DECIMAL` / `TRY_TO_DATE` は失敗を NULL にする。**静かに消えるので必ず数える。**

```sql
SELECT raw_value, COUNT(*) AS n
FROM src
WHERE raw_value IS NOT NULL
  AND TRY_TO_DECIMAL(REGEXP_REPLACE(TO_VARCHAR(raw_value), '[^0-9.-]', ''), 18, 2) IS NULL
GROUP BY 1 ORDER BY 2 DESC
```

出てきた値を見れば、削り漏れの文字（`¥` `,` 全角スペース `%` `△` `▲`）が分かる。
0件になるまで `cleansing-recipes.md` の定型句を足す。

**NULL にならない失敗もある。** `TRY_TO_NUMBER` は scale=0 なので、`0.35` を **`0` として通す**。
比率・構成比の列が全部 0 になっていないかを、変換失敗とは別に確認する
（`SELECT COUNT(*) FROM src WHERE ratio = 0` が総件数と一致したら、それがこれ）。

**空欄と変換失敗を混同しない。** 協和①は備品列の69%が空欄で、これは正常。
`COALESCE(..., 0)` を入れ忘れると合計が丸ごと NULL になる。

## 5. グレインの検算（行数が増えていないか）

JOIN でキーが重複すると行が増え、金額が水増しされる。**合計を見る前に行数を見る。**

```sql
SELECT join_key, COUNT(*) AS n
FROM master GROUP BY 1 HAVING COUNT(*) > 1 ORDER BY 2 DESC
```

マスタ側にキー重複があれば、JOIN前に `GROUP BY` で潰すか、
どの1行を採るかのルールを決める（勝手に `MAX` で潰さない。ユーザーに確認する）。

## 6. 区分の全列挙（CASEの網羅性）

```sql
SELECT kubun, COUNT(*) AS n, SUM(amount) AS amt
FROM src GROUP BY 1 ORDER BY 2 DESC
```

- `CASE` のマッピングがこの結果を**全部覆っているか**
- **`合計` `Total` のような集約行が混ざっていないか** ← 混ざれば二重計上
- 空欄・空白だけの区分がないか

協和①では区分が空の4行に粗利 39,632,386 があり、原本のTotalに含まれない値だった。
「Total行は無い」ことを確認したうえで、その4行は除外した。**除外したものは必ず報告する。**

### 6-1. 合計行の混入は「キーの母集合」から入ってくる

合計行は、その行を持つソースを**キーの母集合に混ぜた瞬間**に紛れ込む。
協和では ③SPD収支管理表に合計行が8件あり、金額が個別94件の合計と**完全に一致**していた
（経費 889,061,547 / 管理料 762,093,595）。つまり**丸ごと2倍計上**。

原因は SQL 側にあった。**キーの母集合を4ソースの和集合（`UNION`）で作っていた。**
原本は「①68期実績が土台で、③は VLOOKUP で列を足すだけ」なので、
①に無い合計行は本来そこに存在しえない。

**対処: 母集合は土台ソース1本から作る**（`base-join-skeleton.md` §1）。
`spd_measure` を母集合から外しただけで、合計行は自動的に落ちた。

見分け方: **「金額が他の行の合計と一致するキー」を探す。** 名前で判断しない
（`計` が付いていても独立部門のことがある — 協和の「160 パラS営業部計」がそれ）。

### 6-2. 合計が 0 でも「データが無い」とは限らない

符号が相殺しているだけのことがある。**配賦済みの表は必ずこの形になる**
（出す側がマイナス・受ける側がプラスで、総和は 0）。

協和では「科目695 プロ本部経費」の実績額合計が `0.0` で、長らく**未受領データ扱いで
ブロッカーになっていた**。実際には取込済みで、本部6部門が −124,824,964、
エリア14拠点が +124,824,964 という配賦済みの表だった。

```sql
-- 合計が0のときは必ず符号で割る
SELECT SIGN(amount) AS sign, COUNT(*) AS n, SUM(amount) AS amt
FROM src WHERE item_cd = '695' GROUP BY 1
```

そのうえで、**引き算に使ってよいのはどちら側か**を決める。協和の残余計算は
「エリア（受ける側）だけ」を使う。本部（出す側）を混ぜると残余が歪む。

## 7. 時間軸 — 月を結合キーにする前に、全ソースの月分布を1本で出す

```sql
SELECT MIN(month) AS from_m, MAX(month) AS to_m, COUNT(DISTINCT month) AS months, COUNT(*) AS n
FROM src
```

想定期間と違えば、取込ファイルの差し替えか期の取り違え。

**単体で見ても足りない。結合するソース全部を1本の `UNION ALL` で並べる。**
月が噛み合っていないと `ON a.月 = b.月` が**エラーを出さずに全件マッチ0**になる。

```sql
SELECT 'AMEX' AS src, month, COUNT(*) AS n FROM amex_measure  GROUP BY 1,2
UNION ALL SELECT 'LABOR', month, COUNT(*) FROM labor_measure  GROUP BY 1,2
UNION ALL SELECT 'PRO',   month, COUNT(*) FROM pro_measure    GROUP BY 1,2
ORDER BY 1, 2
```

協和の実測（2026-09-04）:

| ソース | 月 | 行数 |
|---|---|---|
| AMEX | 2026/05 | 535 |
| 人件費 | 2026/05 | 4,037 |
| プロ経費 | 2026/06 | 2,642 |
| 予算対比表 | 2026/06（開始=終了=202606 の単月） | 2,118 |
| ①68期実績 | `2026-06-01`（**ダッシュ書式**。実体は期累計） | 7,982 |

ここから2つの別々の問題が出る。**混ぜて考えない。**

1. **結合の問題** — 05 と 06 は永遠に噛み合わない。土台①が期累計である以上、
   この列は時間軸ではなく**ファイルのスタンプ**。→ 月を結合キーから外し、
   出力グレインを「得意先1件＝1行（期単位）」にする。
   ただし将来複数月が入ると静かに二重計上するので、
   **各ソースの `COUNT(DISTINCT month) = 1` を検算に残す。**
2. **意味の問題** — `販管費(6月) − AMEX(5月) − 人件費(5月)` は論理的に成立しない。
   結合キーを外しても解決しない。**これは顧客確認事項**であって、SQLで直すものではない。
   進行はブロックせず、**金額スケールの比較で破綻していないことだけ先に確認する**
   （協和は残余が総額の約88%で正の値 → 数値としては破綻なし、論理としては要確認）。

**書式がソースごとに違う点にも注意。** 同じ「月」でも `2026/05/01`・`202606`・`2026-06-01`・
Excelシリアル値が混在する。`DATE_TRUNC('MONTH', ...)` で揃える前に、生値を見る。

## 8. 合わないときの切り分け順

上から順に見る。逆から見ると時間を使う。

```
1. 行数        … JOINで増えていないか（§5）
2. 対象期間    … 期・月の範囲は合っているか（§7・期ズレ）
3. 重複        … 合計行・Total行の混入（§6）
4. 除外条件    … 落としているものは正しいか（§3）
5. 掛け目・比率 … 分母の取り違え（§1の「全月で一定割合」）
```

## 9. 回答に載せる形

検算結果は表で出し、**判定を書く**。数字だけ並べない。

```
■ 検算（STEP2 人件費按分）
  月       配賦元        配賦先        差    判定
  2026/04  12,345,678   12,345,676     2    ✓ 端数
  2026/05  11,000,000   11,000,000     0    ✓
  2026/06  10,500,000    9,200,000  1,300,000  ✗ 分母0の月あり → §1
```
