# 運用手順（会話のターン設計）

案件に着手したら、SQLを1行でも書く前にこの文書を開く。
プロジェクト指示に載っているのは骨格だけで、各ターンで何を出すかはここが正。

全体は4ターン。ユーザーの手が動くのは **ターン1の指摘・ターン2の決定と正解値の提供・
ターン3以降のSQL実行** だけ。原本 Excel の添付は求めない（`report-input.md` §5）。

```
[ユーザー] レポートHTML添付 +「この案件で始めて」
   ↓
[ターン1] 取得ログ ＋ 復唱 ＋ 突き合わせ表          ← SQLは書かない
   ↓ ユーザー: 違うところだけ指摘
[ターン2] ロジックの復唱（付録の数式が根拠・根拠なし列も明示）＋ 類型の判定 ＋ 質問（1回で）
   ↓ ユーザー: 決定
[ターン3] 事前検証クエリ（番号付き）＋ SQL（1区分）＋ 事後検算 をセットで
   ↓ ユーザー: 実行して結果を貼る／スクショ
[ターン4] 検算の突き合わせ → 次の区分へ（3-4を繰り返す）
   ↓
[最終]   全区分を UNION ALL した統合SQL ＋ 最終検算 ＋ 出力仕様 ＋ 計算明細 ＋ 案件メモ
```

---

## ターン1 — 取得ログ・復唱・突き合わせ（SQLは書かない）

### 1-a. 何を取りに行くかを先に言う

黙って調べない。違う案件・違うワークスペースを掴んだときに、
ユーザーがその場で止められるようにするため。

```
■ 案件 = 協和医科器械
  顧客マスタ B列照合 → M列 198 → ゼロ埋め 0198
  クエリ147 → 28アセット（取込済み）
  クエリ145 → 376カラム 取得
```

ワークスペースIDはスプレッドシート「顧客マスタ【kpiee】」から引く
（`15FgI-clo36-bKBkOdP9dCI03xZiuGxc0cFgJB_C_fAo` / シート`顧客マスタ` / ヘッダー5行目 /
B列=案件名（daX管理名称）・M列=ワークスペースID）。M列はゼロ埋めされていないので4桁に整える。
→ クエリ147でアセット一覧 → クエリ145（アセット名は空文字）で全物理カラム名。
手順とAPIの癖は `physical-columns.md`・`data-sources.md`。

**このターンで止まってよい例外が1つある: 顧客マスタ M列が空でワークスペースIDが確定しないとき。**
クエリ146で候補を出して確認を求め、返事を待つ。**社名検索の結果を自動採用しない** —
部分一致は静かに別会社を掴む（`サイバー` → 2社）。1件しかヒットしなくても正しい保証はない。
ここを勘で進めると、以降の突き合わせも検算も全部別の案件の数字になる。

### 1-b. レポートを復唱する

添付が大きいとチャンク検索になり、付録が静かに欠けることがある。復唱がその検出装置。
読めたものを表で出して確認を取る（詳細は `report-input.md`）。

1. 最終アウトプットのファイル・シート・行数・グレイン・キー列
2. 受領ファイルの役割分類（元データ／マスタ／中間／最終）と件数
3. 表ごとの推定キー
4. 列単位の数式 lineage を「何件読めたか」件数で明示
5. 付録の欠落（「23表中8表のみ掲載」など）
6. 未確定事項（03-A/B/C、Q-01〜）

### 1-c. 取込状態を判定して突き合わせる

**先に取込状態を判定する。147が0件なら取込前** — レポートは取込より前に出るのが普通で、
これは例外ではない。その場合は物理名をプレースホルダ（`<①売上>`）で残したまま
SQLの構造を完成させ、併せて取込設計（縦持ち／2段ヘッダーの潰し方）を提案する。
**物理名を捏造しない。** 詳細は `physical-columns.md` §0・§7。

取込済みなら、取得後に必ず突き合わせて結果を報告する。

- レポート付録の列数 vs 取得した列数
- 論理名の並び vs `_1` `_2` … の並び
- 型トークン（`_STRING_` の金額列 → クレンジング必須）

**一致は1行でまとめ、不一致だけを目立たせる。** 全一致でも「◯列すべて一致」と必ず書く。
黙って進めない。**列数が合わないときは取込ミスと決めつけない** —
横持ち→縦持ち変換の実例がある（`physical-columns.md` §4）。

クエリ147にあって145に列が返らないアセットは加工ジョブ。その中身を使うときだけ、
SQL本文か出力列をユーザーに見せてもらう。

### 1-d. 配賦があれば軸を判定する

レポートに按分・配賦の工程があれば、工程ごとに軸を判定して表で出す
（組織軸＝配賦機能／得意先・商品・担当者などの軸＝SQL）。`allocation.md` §6。
どちらで実装するかの決定はユーザーに委ねる。組織マスタへの登録は業務側に副作用が出る。

## ターン2 — 計算ロジックの復唱と質問（まとめて1回）

### 2-a. ロジックを「1指標＝1行」で書き起こす — 根拠は付録の数式だけ

分子・分母まで開いて書く。使える根拠は**レポート付録に載った Excel 数式の原文**まで。
`03 ロジックの確認` は要約なので、SQLの根拠には使わない。
**原本 Excel は見られない前提。** 添付を求めない。付録に無いものを推測で埋めない。

まず最終アウトプットの列を3つに仕分けて表で出す。

| 区分 | 扱い |
|---|---|
| 付録に数式がある | 原文を引用して「1指標＝1行」に展開する |
| 付録に数式が無い | **根拠なし。** SQLに書かず、プレースホルダ＋コメントで残す |
| 数式そのものが存在しない列（手入力・手作業転記） | 手入力であることを明示する |

「メイン39列に対し付録の数式は9件」なら30列が2段目に落ちる。
**その件数をそのまま出す。埋まっているように見せない。**
協和は手入力が42組あり、レポートの Q-02 として顧客確認に回っている。

根拠なしが多いときは、書き進める前に選択肢を出して判断を仰ぐ:

- (a) オンボーディングAI側でレポートを再生成し、数式 lineage を増やす ← 根本はこちら
- (b) 根拠なし列を未確定のまま構造に残し、後から1か所直せば済む形で進める
- (c) その列の**あるべき数値**をユーザーに確認してもらい、逆算で式を当てる

### 2-b. 付録の数式を読むとき落としやすい3つ

数式原文が載っていても、次の3つは読み飛ばすと**エラーが出ないまま数字が狂う**:

1. 金額の**出所シート**（`VLOOKUP(D6, 拠点別経費!...)` のどこを引くか）
2. 合計の**項の数**（`Z = SUMIFS(S)+SUMIFS(T)+SUMIFS(U)+SUMIFS(X)` は4項）
3. 分母の**母集合条件**（`SUMIFS(L:L, B:B, B, L:L, ">0")` — 正のものだけ）

協和ではこの3つが揃ってズレたまま動くSQLができ、検算で捕まったのは1つだけだった。
当時は原本を読んで発覚したが、**今はその退路が無い。付録の原文を1文字ずつ読む。**

付録に該当の数式が無ければ、この3つは**「不明」と書く。ユーザーに丸投げしない** —
原本を見ないかぎりユーザーも答えられないので、聞いても問題を移すだけになる。
代わりに 2-a の (c) — あるべき数値からの逆算 — に回す。

配賦があるなら、先に3つを確定させる:
**配賦元の総額の出所／既配賦として引く項目の一覧／分母の母集合条件**
（`allocation-sql-skeleton.md` §0）。付録から取れなければそこも「不明」とし、
配賦SQL全体を暫定扱いだと明記する。

### 2-c. 類型を決める（ここを間違えると作り直しになる）

最終アウトプットの1行が何かで骨格が決まる。判定を1行で書いて確認を取る。

| 最終アウトプットの1行 | 骨格 | 参照 |
|---|---|---|
| 1エンティティ（得意先1件） | 土台に `LEFT JOIN` で列を足す | `base-join-skeleton.md` |
| 区分×日付（販路×日） | 区分ごとのCTEを `UNION ALL` | `channel-aggregation.md` |
| 金額を配賦先へ移し替える | CTEを縦に積む | `allocation-sql-skeleton.md` |

Excel の数式が `VLOOKUP` の連なりなら土台＋列足し型。区分ごとにシートが分かれていれば区分別統合型。
1案件に複数の類型が同居することはある（協和は STEP1 が土台＋列足し、STEP2〜4 が配賦）。
**工程ごとに分けて書く。1本のCTEに混ぜない。**

### 2-d. 未確定事項を全部まとめて聞く

1つずつ小出しにしない。後から全区分を直すのは高コスト。
聞くのは、レポートに書かれていないもの:

- **検算の正解値**（必須）。区分ごと・工程ごとの合計が**いくつになるべきか**を、
  顧客帳票か kpiee 画面から拾って渡してもらう。原本を見られないので自分では作れない。
  これが無いと検算が成立せず、出したSQLは「未検証」のままになる（`reconciliation.md` §0）
- 根拠なし列の**あるべき数値**（2-a の (c) を選んだ場合）。逆算の材料になる
- 出力グレイン（月別か期累計か、日次で持ってレポート側で丸めるか）
- 税込か税抜か
- 掛け目（手数料・アフィリエイト料率など）とその根拠
- 端数処理（四捨五入か切り捨てか、整数化するか小数のまま持つか）
- 対象期間と日付の基準（発生日／計上日／クリック日）、締め日のズレ
- 同一キー重複時の扱い（合算か上書きか）
- 分類定義の出所（マスタ表か、キャンペーン名からの読み替えか）
- 空白時の `'不明'` を各区分のCTEで入れるか、統合後の最終SELECTで一括か
- 区分の分岐条件（どの列のどの値で自社／アフィリ／その他を分けるか）

未確定のまま進めてよいものは「未定のまま進めます。あとで1か所直せば済む形にします」と
明言して先へ進み、スイッチとして構造に残す。**質問で止めない。**

## ターン3 — 事前検証 → SQL → 事後検算 を番号付きで渡す

1回答＝1区分（1工程）。そのまま貼れる完成形。**検算は必須の同伴物**で、SQLと同時に出す。
ユーザーが実行担当なので、検算を次のターンに回すと往復が倍になる。

### 3-a. 事前検証を本体より前に置く

本体はエラーを出さずに壊れることがあり、そのときは検算の数字を見ても原因が分からない。
協和では `TRY_TO_DATE` の1引数版が NULL を返し、AMEX の実績が全消えする状態で本体を書いていた。

```
検証0  変換の成否（日付・金額の生値 × 変換結果 × 件数）
検証1  SQLが黙って置いている前提の反証（「部門コード = 拠点」など）
検証2  キーの一意性（1キーに突合先が複数ないか）
検証3  未マッチのキーとその金額
検証4  残余マイナスの行
本体   SQL
```

分類キーは全列挙して、CASE のマッピングが**この結果を全部覆う**ことを確認する
（推測で6件だけ書いて残りを ELSE に落とすのは事故）。結合する全ソースの月分布も
1本で並べる（噛み合わないと `ON 月` が無言で全件0になる）。
順序と型は `reconciliation.md` §0-b。

### 3-b. 渡すときに必ず添える

- **どのアセットを入力に選ぶか**（選んでいないと `存在しません` エラーになる）
- **1文ずつ実行**（複数文は `position …` の構文エラー）。**番号を振る**
- **検証0 が落ちたら 1 以降は流さない**（前提が崩れた結果を見ても意味がない）
- 別名は**中間CTEが ASCII、最終SELECTが日本語**（顧客の明細画面に出るため。`SKILL.md` §2）。
  最終SELECTは1か所にまとめ、「`unexpected …` で落ちたらこのブロックだけ貼り直し」と添える
- コピーが難しい環境なら**スクショで足りる形**にする（列を絞る・`LIMIT 1`）
- **出力仕様**（順番 → 別名 → 予測物理名 → **原本の列** → 下流での用途）。ジョブ登録で別名は
  消えるので、これを書かないと下流が参照できない。SQL本文の先頭にコメントで入れる。
  **原本の列（シート・列記号）を必ず1列持つ** — 別名を見出しに合わせても
  どのシートの何列目かは残らないので、受け取った側が原本と照合できない
  （`physical-columns.md` §8-0）
- **計算明細**（代表1件を階段式に開いたもの）。回答本文に書く。出力仕様とは別物で、
  読む人が違う（顧客・検算者）。**中間値を出力列に残していないと書けない** ——
  同じ列が製品の「数値の明細表示」にそのまま出る（`calc-spec.md`）

### 3-c. 作る順番

母集合は土台ソース1本から。簡単な区分・工程から着手し、都度検算する。
分岐やマスタ突合、残余の配賦は後回し。途中でクレンジングを挟む（`cleansing-recipes.md`）。
SQLを出す前に `validation.md` のチェックリストを通す。

## ターン4 — 検算を突き合わせて次へ

区分（工程）ごとの合計を出し、**ターン2でユーザーから受け取った正解値**と並べて可否を判定する。
正解値が来ていない項目は「未検証」と明記する。合ったことにしない。
合わなければ **行数 → 対象期間 → 重複 → 除外条件 → 掛け目** の順で切り分ける。

- **期ズレに注意**（最終アウトプットが67期、土台が68期という実例がある）
- **月を結合キーにする前に、全ソースの月分布を1本のクエリで並べる。**
  協和は AMEX・人件費が5月、プロ経費・予算が6月、土台①が期累計で、
  月を結合キーから外す判断になった
- 差が数円〜数十円なら端数として合格。**桁が違う差だけを追う**
- **合計が0の項目を「データ無し」と決めつけない。** 符号が相殺していることがある
  （配賦済みの表は必ずこの形になる）。`SIGN()` で割って見る
- **配り残しは異常とは限らない。** 配賦先が1件も無い部門は配りようがない。
  内訳を出して正常・異常を判定してから報告する

エラーが返ってきたら推測で原因を1つに決めず、実行SQL全文とエラー原文をもらう。
直すときは該当箇所を含むCTE単位の完成形を返す。

詳細は `reconciliation.md`。

## 最終ターン — 統合と引き継ぎ

全区分がそろったら、統合SQL（`UNION ALL`）と最終検算を出す。
併せて案件メモの更新版を回答末尾に載せる（様式は `case-memo-template.md`）。

**出力仕様を必ず添える。** 統合SQLの別名は kpiee のカラムラベル（論理名）になるが、
**SQLジョブが別のジョブ出力を FROM で参照するときは
`DC_SQL_JOB_<アセットID>_<型>_C<連番>` でしか書けない。** 参照経路が2つある。
順番 → 別名 → 予測物理名 → **原本の列（シート・列記号）** → 下流での用途 の表を出し、
SQL本文の先頭にも同じ表をコメントで埋め込む（作り方は `physical-columns.md` §8-0）。
**原本の列は145の論理名を一次情報にし**（ターン1で全件取ってあるはず）、
145に無いシート名・列記号だけを付録から補う。埋まらない列は `—`。
アセットIDは登録するまで決まらないので `xxxx` で伏せ、**登録後に145を流し直して確定させる**
のが最後の一手。ここを飛ばすと、次の担当者は SQL 本文の別名を FROM 側に書いて落ちる
（協和で実際に `指定カラムが存在しません` で詰まっている）。

**計算明細も添える。** 金額最大の得意先1件を階段式に開き、各行に出どころ（アセット名＋論理名）を
書く。出力仕様が「名前の対応表」なら、これは「金額の導出過程」で、読む人が違う。
**中間値を出力列に残したかがここで効く** — 落としていると明細が書けず、顧客が製品の
「数値の明細表示」を開いても最終値1列しか出ない（型と体裁は `calc-spec.md`）。

**最重要は「現在地」と「踏んだ罠」。** カラム定義は Redash から取り直せるが、この2つは取り直せない。
未解決は**顧客確認／製品チーム確認／自分の宿題**の3つに分けて書く（混ぜると、待つだけのものと
自分が動けば済むものの区別が付かなくなる）。**解決した項目は消さず、結論を残す** —
協和の「プロ本部経費が未受領」は実際には取込済みで、合計が0に見えていただけだった。
