# 計算明細（説明のための明細）

SQLを渡すときに添える2つ目の明細。**出力仕様とは別物で、片方で代用できない。**

| | 出力仕様（`physical-columns.md` §8-0） | 計算明細（この文書） |
|---|---|---|
| 示すもの | 列の**名前**の対応 | 金額の**導出過程** |
| 読む人 | 次の担当者・レポート定義を作る人 | **顧客・検算するユーザー** |
| 置き場所 | SQL本文の先頭コメント | **回答本文** |
| 無いと起きること | 下流が参照名を作れない | 「この数字どこから来たの」に答えられない |

出力仕様に物理カラム名を書くのは、それが下流の参照名だから。
計算明細に物理カラム名を書いてはいけない。読む人が違う（§4）。

**さらにもう1つ、製品側の「数値の明細表示」がある（§6）。**
レポートのセルを右クリックして出るモーダルで、顧客が自分で開く。
この文書の明細は「回答に書く説明文」、§6は「製品画面に出るもの」。
**§6に何が出るかはSQLの出力列が決めるので、構築時の設計対象になる。**

## 1. 型 — 代表1件を階段式に開く

```
【計算明細】拠点003・◯◯商事・2026年6月   ※数値は例

  拠点の販管費 総額                10,000,000   ⑥拠点別経費「★販管費合計」
− すでに配り終えた分（4項目）       6,000,000
    ・SPD経費合計                  1,500,000   ③SPD収支管理表「経費合計」
    ・AMEX手数料                     800,000   [加工]AMEX手数料計算「手数料金額」
    ・エリア人件費                 2,200,000   [加工]得意先エリア人件費「得意先_エリア人件費」
    ・プロ本部経費                 1,500,000   [加工]プロ経費「実績額_按分」
= 残り販管費合計                    4,000,000

  拠点内の売上合計（売上が正の得意先のみ）
                                 200,000,000   ①68期集計得意先別実績「売上」
  この得意先の売上                  6,172,500
→ 拠点内売上構成比                     3.086%

→ 配賦後の残り販管費                  123,450   ← 出力の最終値
```

守ること:

- **代表1件だけ出す。** 全件は出さない。選ぶのは金額最大の行か、ユーザーが指定した行。
- **1行1ステップ。** 「総額 − 既配賦 = 残り」を1行に圧縮しない。圧縮すると、
  どこで数字が狂ったかを指す場所が無くなる。
- **各行に出どころを書く。** アセット名＋論理名。式だけ書いて出どころを省かない。
- **中間値を丸めない。** 表示の桁区切りだけ。丸めると最終値が合わなくなり、
  「明細と結果が違う」という別の問題を作る。
- **最終行はSQL出力の該当行と一致すること。** 一致しない明細は出さない。
  ここが検算そのものになる。

## 2. 中間値を列として残す（SQL側の要件）

**階段の各行が、SQL出力の1列に対応していなければ明細は書けない。**
合算して1列にすると、どの工程が効いたか追えなくなる
（`allocation-sql-skeleton.md` §6 と同じ理由）。

協和の対応:

| 階段の行 | 出力列 |
|---|---|
| 拠点の販管費 総額 | `branch_sga_total` |
| すでに配り終えた分（4項目） | `branch_allocated_total` |
| 残り販管費合計 | `residual_sga` |
| 拠点内売上構成比 | `sales_ratio_in_branch` |
| 配賦後の残り販管費 | `sga_after_alloc` |

内訳4項目まで列で持つかは、レポート側が既にデータファイル指標として
持っているかで決める（重複定義になるなら列にしない。明細には出どころだけ書く）。

## 3. 根拠が無い行は「不明」と書く

付録に数式が無い工程は、階段の該当行に `—（根拠なし・未確定）` と書く。
**それらしい数字で埋めない。** 明細は説明資料なので、埋めた嘘がそのまま顧客に渡る。

```
− 手数料調整                        —（根拠なし。付録に数式が無い。Q-02 で顧客確認中）
```

## 4. 顧客に見せる体裁

- **物理カラム名を書かない。** `DC_SQL_JOB_0031_DOUBLE_CF` は読む人に意味が無い。
- **中間CTEのASCII別名を書かない。** `residual_sga` ではなく「残り販管費合計」。
  最終SELECTの別名は帳票の見出しにしてあるので、そのまま使える。
- 使うのは**帳票の見出し**。出力仕様の `原本の列` 列がそのまま表記ソースになる
  （`physical-columns.md` §8-0）。**2つの明細はここで繋がる。**
- 金額は桁区切り、単位を書く。比率は小数第3位まで。

## 5. どこで出すか

| タイミング | 出すもの |
|---|---|
| ターン3（区分ごと） | その区分の計算明細を1件。SQLと検算クエリと同時に |
| 最終ターン | 統合SQLの計算明細を1件（金額最大の得意先） |
| 案件メモ | 「確定した計算式」の直後に代表1件を貼る。次の担当者が**数式と実数を突き合わせられる** |

案件メモに実数入りの明細が1件あると、次の会話で「この式でこの数字になる」が
1目で確認できる。数式だけだと、読めても正しく実装されているかは分からない。

## 6. 製品の「数値の明細表示」— SQLの出力列がそのまま明細になる

レポートのセルを**右クリック → 「数値の明細表示」**で、その数字を構成した元の行が
モーダルに出る。顧客が自分で開く機能。

根拠（`dx-kpiee`）:
`frontend/kpiee/src/locales/features/reports.ts` の `context_menu.open_detail_modal`、
`features/reports/components/CellDetail/`、
API `POST /workspaces/{workspace_id}/reports/{report_id}/cell_details`。

| 明細に出るもの | どこから来るか |
|---|---|
| **行** | その指標が指すデータファイルのレコード（マスタ結合も可） |
| **列** | 同じデータファイルのカラム。**ユーザーがモーダルで選ぶ**（選択は localStorage 保存） |
| **列見出し** | カラムの**論理名**（レスポンスの `label`）。物理名は出ない |
| **配賦フラグ** | `isAllocation`。**製品の配賦機能で作られた値だけ true** |

モーダルもコンテキストメニューも製品機能なので触れない。
**構築時に決められるのは「明細に何が出るか」だけで、それはSQLの出力列がそのまま決める。**

守ること:

- **中間値を出力列に残す。** 残さないと、顧客が明細を開いても最終値1列しか出ず
  「なぜこの金額か」に答えられない。§2の対応表が**そのまま明細の中身になる**。
  「中間値だから検算クエリに逃がす」と判断する前に、その列が明細に必要かを見る
- **論理名（＝SQLに書いた別名）が顧客の画面に出る。** だから
  **最終SELECTの別名は帳票の見出しで書く**（`SKILL.md` §2）。ASCII を貫くと
  `sga_after_alloc` が顧客に見える。製品側で `column_label` は後から変更できるが、
  **その運用にしない** —— 直し忘れが無症状で顧客画面に残る。
  SQLに書いておけば、壊れたときは構文エラーで必ず気づく
- **`isAllocation` は SQL では付かない。** 製品の配賦機能で計算すれば明細上で
  配賦分と判別でき、配賦基準も辿れる。SQLで書くと普通の数値列になり、
  「これは配賦された金額だ」という情報が画面から消える。
  → `allocation.md` §4（製品機能かSQLか）の判断材料に加えること
- レポートが既にデータファイル指標として持っている値をSQLでも出すと二重定義になるが、
  **明細に必要な列はその例外**。どちらの指標を顧客が開くのかで決める
