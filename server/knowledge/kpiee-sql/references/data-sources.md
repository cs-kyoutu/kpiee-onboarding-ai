# データの取り方（kpiee Redash / kpiee MCP）

「アセット名・カラム名・物理カラム名」の対応表や、実データの中身は、
**ユーザーに手で貼ってもらう前に自分で取りに行く。** ルートは2系統。

| ルート | できること | できないこと |
|---|---|---|
| kpiee Redash コネクタ（`list_queries` / `get_query_result`） | 保存済みクエリの実行。**ワークスペースID・アセット一覧・物理カラム名の取得**。ワークスペースをまたいで引ける | 任意のSQLは書けない。保存済みクエリとそのパラメータの範囲だけ。実データの値は返らない |
| kpiee コネクタ（`execute_sql` ほか） | 任意の SELECT で値の確認・集計 | **見えるのは権限のあるワークスペースだけ**（共用アカウント `sp_share` は ws4「データX」のみ）。顧客ワークスペースには入れない |

使い分けは明確。**カラム定義は Redash、値の検証は `execute_sql`。**
顧客案件では `execute_sql` が使えないのが通常なので、**値の確認はユーザーに依頼する**
（原本 Excel は見られない前提なので、そこから読む手は無い）。
物理カラム名は Redash で取れるので依頼しない。

## 1. kpiee Redash — 物理カラム名の自動取得

**手順の詳細は `physical-columns.md`。** ここでは所在だけ。

| ID | 名前 | パラメータ |
|---|---|---|
| 146 | `[調査] ワークスペースID検索` | なし（シートが空のときの補完用） |
| 147 | `[調査] アセット名検索` | `ワークスペースID` |
| 145 | `[調査] 物理カラム名検索` | `ワークスペースID` / `アセット名` |

基本形は「**シート「顧客マスタ【kpiee】」B列（案件名）→ M列（ワークスペースID）**
→ 147で取込済みか判定 → 145に空アセット名で投げて全カラム取得」。
ワークスペースIDを社名検索で当てにいかない。M列が空のときだけ146で補完する。

**`b→dash` の Redash と混同しない。** あちらには `データファイルカラム検索`
（パラメータが `アカウントID`、ID 21・20・142 など）があるが、kpiee 側には存在しない。
kpiee で同じ ID を叩くと全く別の監視クエリが動く（例: kpiee の 157 は滞留監視）。

### API の癖

- `get_query_result` は **パラメータ付きクエリなら `parameters` を明示的に渡す**。
  省略すると `400 BAD REQUEST`（既定値があっても補完されない）。
- 結果はページングされる。`total_row_count` / `total_pages` を見て `page` を進める。
  `limit` を大きめ（100〜200）にしてページ数を減らす。
- `max_age` の既定は1800秒。取込直後は `max_age: 0` で引き直す。
- **`list_queries` の `q` は当てにならない。** 名前に「データファイル」が入っている
  クエリが `q=データファイル` で0件になる。`q` なしで `page_size` を大きくして目視で探す。
- `filters` が使える。146 で顧客名から絞るのはこれ（`operator: "contains"`）。
- 顧客の実データが返る。回答に貼るのは必要な範囲だけにする。

### 落ちていることがある

kpiee Redash は 2026-08-13〜09-02 に3週間以上停止していた（`fetch failed` / ホスト無応答）。
2026-09-04 に復旧を確認。落ちているときは **その旨を明示** したうえで、
SQLジョブ画面 `入力一覧` のスクリーンショットを依頼する旧手順に落とす。推測で埋めない。

## 2. kpiee MCP（任意のSELECTを発行する）

```
get_basic_information      用語と制約（初回のみ）
list_workspaces            対象 workspace_id
list_table_data_files      表形式データ（予算は template_type=budget）
list_record_data_files     履歴データ
list_master_tables         マスタ（階層データ）
get_table_data_file_detail table_name とカラム定義
get_master_table_content   マスタの中身
execute_sql                SELECT のみ発行
```

`execute_sql` は `workspace_id` `sql` と、参照するデータファイルの `data_file_ids` が必須。
`data_file_ids` は閲覧権限の判定と参照先の制限に使われるので、`FROM` に出てくる
データファイルのIDを全部入れる。別のIDのテーブルを混ぜると `FORBIDDEN`。

制約：SELECT のみ（`SHOW TABLES` も不可）／実行45秒／10,000行／ツール呼び出し60回・分。
行数上限があるので、生データを全件取らず `GROUP BY` して返す形にする。

**顧客ワークスペースは見えない。** これが常態。値の確認が必要なら §3。

流す順番は `kpiee-data-model.md` §2 の確認クエリを参照。

## 3. 値の確認をユーザーに頼むとき

物理カラム名は §1 で取れているので、**渡すのは完成した確認クエリ1本**。
「`SELECT *` して結果を貼ってください」ではなく、見たいものを名指しした形にする。

```sql
-- 例: 区分の全列挙と金額の合計（物理名は取得済みのものを埋めて渡す）
SELECT IMPORT_30014_STRING_2 AS kubun, COUNT(*) AS n,
       SUM(TRY_TO_DECIMAL(REGEXP_REPLACE(TO_VARCHAR(IMPORT_30014_STRING_5), '[^0-9.-]', ''), 18, 2)) AS sales
FROM IMPORT_30014 GROUP BY 1 ORDER BY 1
```

依頼時の注意（実測）:

- **SQLジョブは1文のみ。** 複数文を貼ると `position …` の構文エラーになる。1本ずつ渡す。
- **入力に選んだアセットしか `FROM` に書けない。** どのアセットを選ぶかを明記する。
- **日本語別名は VDI 経由で壊れることがある**（クリップボードでマルチバイトが化ける）。
  ユーザーに実行してもらう確認クエリの別名は ASCII にする。
- VDI からのコピーが難しい環境がある。**スクリーンショットで足りる形**にしておく
  （列を絞る・`LIMIT 1` にする）。
