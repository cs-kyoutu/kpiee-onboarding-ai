# 配賦（はいふ）— 製品機能でやるか、SQLで書くか

「本社費・共通費のように、特定の部署に直接ひもづけられない費用を、
合理的な基準で各部署に配分する」のが配賦。会計上の概念で、kpiee には
**製品機能として配賦がある**（`kpiee-designs/docs/feature/allocation/`）。

このスキルの判断は1つだけ。**その按分は製品機能でできるのか、SQLで書くのか。**
先に機能の形を知らないと判断できないので、まず §1〜3、判断は §4。

## 1. kpiee の配賦機能の構造

設定は3つの部品でできている。

| 部品 | 何を決めるか | テーブル |
|---|---|---|
| **配賦元** | どのデータファイルのどの金額項目を／どの組織・科目の分を配るか | `allocations.source_*` |
| **配賦先** | どの組織へ／どの科目として置くか | `allocations.target_*` |
| **配賦基準** | どういう割合で配るか | `allocation_criteria` |

配賦先の科目は2通り（`item_mapping_type`）。

- `same_as_source` — 配賦元と同じ科目のまま配る
- `different_from_source` — 別の科目にまとめて配る（統合配賦）

**配賦元の金額を残すか消すか**は `keep_source_amount`。
以前は基準ごとに設定できたが、**配賦設定（allocation）全体で1つに統一された**（IMP_KP001222）。
残さない設定なら、配賦元から `DEDUCTION` レコードが立って金額が引かれる。

## 2. 配賦基準は3種類しかない

| 方式 | 内部名 | 割り方 |
|---|---|---|
| 等分 | `equal_ratio` | 配賦先の組織数で均等割り |
| カスタム比率 | `custom_ratio` | 手で決めた比率（合計は自動で100%に正規化） |
| **科目基準** | `account_based` | **指定した科目の金額に比例**（売上高比・人数比など） |

実務で使うのはほぼ `account_based`。「訪問数で按分」「売上構成比で按分」はこれに当たる。
**基準値は月ごとに計算される**（分母＝その月の配賦先各組織の基準科目金額の合計）。

## 3. 多段階（ステップ）と制約

### ステップ

`allocation_steps` に `step_order` を持ち、**前ステップの結果を次ステップの配賦元にできる**。
本社費 → 事業部 → 部署、のような段階配賦が組める。
適用期間（`applicable_from/to`、全期間フラグ）もステップ単位で指定できる。

### レコード数の上限（IMP_KP001246）

```
配賦先科目数 × 配賦先組織数 × 月数 ≦ 10,000,000
```

超えると**そのステップが Failed になる**（計算前に検知して中断する）。
OOM対策で入った制限で、配賦元の組織数は集約されるため条件から外れている。

### 分母が0のときの挙動（IMP_KP001249）

科目基準で、ある月の**配賦先全組織の基準科目金額が0**になることがある
（期中に子組織が増えた、その月のデータが欠損、など）。

| ケース | 挙動 |
|---|---|
| 配賦元金額が0 | 配賦自体が実行されない（スキップ） |
| **基準値の合計が0** | **比率0%として記録。エラーにしない。配賦元の減算も行わない** |
| 基準値が一部0 | 0%の組織には配らず、残りの組織に配る |

以前はエラー（`CriteriaTotalZero`）だったが、正常扱いに変わった。
**SQLで書くときもこの挙動に合わせる**（§5）。

### 計算結果の置き場所

配賦計算はSnowflake上に動的テーブルを作る。

- `ALLOCATION_SOURCE_DF_{datafile_id}_{allocation_id}` — 月×組織×科目に集計した配賦元
- `ALLOCATIONS_{report_id}` — 配賦結果

> **未確認**: SQLジョブの `FROM` からこれらを参照できるかは確かめていない。
> SQLジョブは「登録済みアセットのみ参照可」の契約があるため、たぶん直接は引けない。
> 配賦結果をSQLの入力にしたい場合は、先にこの点を製品チームに確認すること。

## 4. 判断 — 製品機能かSQLか

### 4-1. 「組織」の正体（誤解しやすい）

配賦の軸は「組織 × 科目」だが、ここでいう組織は**組織図そのものではない**。
実体は階層データ（マスタ）で、`master_types.category` は3種類ある。

```ruby
CATEGORY = { organization:, accounting:, custom: }   # master_type.rb
MAX_CUSTOM_MASTER_TYPES = 100
```

**配賦設定画面の「組織階層」セレクタは `organization` と `custom` の両方を出す**
（`useAllocationSettings.ts` の `filterAndSortMasterTypesByCategory(..., 'organization')` は
`mt.category === primaryCategory || mt.category === 'custom'` で絞っている）。科目側も同じ。

つまり **得意先を「カスタム階層」として作れば、配賦の軸に使える。**
本物の組織図に得意先4,000件をぶら下げる必要はない。
「得意先は組織じゃないから機能では無理」は言い過ぎ。**軸そのものは表現できる。**

### 4-2. それでも SQL になる理由

軸が作れても、次の3つが残る。判断はこちらで行う。

| # | 制約 | 効き方 |
|---|---|---|
| 1 | **レコード上限**（§3） | カスタム階層でも同じ。件数の多い軸は素直に当たる |
| 2 | **配賦元と配賦先が同じ階層** | `allocations` が持つ組織階層は `org_type_id` / `org_table_id` の**1つだけ**。`source_org_codes` と `target_org_codes` は同じ階層内のコード |

> **`custom` はカテゴリ（ラベル）であって階層そのものではない。**
> 担当者マスタと得意先マスタを作れば、どちらも `custom` だが **別々の `master_table`**。
> 同じカテゴリでも別の階層なので、制約2に引っかかる。ここは間違えやすい。
| 3 | **「残余」の概念が無い** | 「販管費合計 − 既配賦分」を直接表せない |

協和医科器械の実例:

```
得意先 4,000件 × 12ヶ月 = 48,000
10,000,000 ÷ 48,000 ≒ 208     ← 配賦先科目が208個で上限（制約1）
```

協和の STEP2 は**配賦元が担当者（人）で配賦先が得意先**、分母は「担当者個人の総訪問数」。
制約2により、担当者と得意先を**同じ1つの階層に同居させる**必要がある
（担当者を親・得意先を子にした木にする）。**そしてこれは実データ上できない。**

```
⑥得意先別訪問数 = 月 × 社員番号 × 顧客No × 訪問数     ← 1行が「社員×得意先」
```

1つの得意先を複数の社員が訪問する。**階層は木構造で子の親は1つ**なので、
同じ得意先を複数の担当者の下にぶら下げられない。多対多は木に入らない。
業務判断以前に構造的に不可。

> 実際、協和の STEP2 は既に SQLジョブとして実装済みだった:
> `得意先毎に訪問数を比率として人件費を按分`（`DC_SQL_JOB_0026`）
> — `社員別訪問数合計`（分母）/ `按分比率` / `得意先_エリア人件費`（結果）を持つ。
> **按分の軸が多対多なら配賦機能は検討するまでもない**、という実例。

**まとめ: 次のどれかに当たったらSQL。**

1. 軸の件数 × 科目 × 月数 が上限に届く
2. **配賦元と配賦先が別の階層／多対多**（← 一番強い。構造的に不可）
3. 「残余」がある

**「按分が複数回ある」ことは理由にならない**（多段階は機能側もステップで対応できる）。
軸が組織図に無い、も理由にならない（カスタム階層で表現できる）。

### SQLにすると失うもの — 明細の配賦フラグ

**製品の配賦機能で計算した値は、レポートの「数値の明細表示」で配賦分として
判別できる**（`cell_details` レスポンスの `isAllocation`。Go側に `buildAllocationQuery` が
別経路で用意されている）。配賦基準も辿れる。

**SQLで書くと、明細では普通の数値列になる。** 「これは配賦された金額だ」という
情報が顧客の画面から消える。顧客が明細を開いて説明を受ける運用なら、
これは機能側を選ぶ理由になる。SQLで行くなら、中間値（総額・既配賦・残余・比率）を
出力列に残して明細で追えるようにする（`calc-spec.md` §6）。

### 判断が付かないときに確認すること

- 「販管費合計 − 既配賦分 = 残余」を配賦画面で表現できるか（**協和で未解決**）
- 配賦結果テーブルをSQLジョブから参照できるか（§3の未確認事項）
- **顧客が明細（右クリック）を開く運用か。** 開くなら配賦フラグの有無が効く

### 配賦機能で行く場合、SQLの役割は縮む

「kpieeが食える形にデータを整える」までになる。
具体的には **月 × 組織コード × 科目コード × 金額** のグレインに揃えて出す。
按分の計算そのものは書かない。

## 5. SQLで書く場合 — 配賦機能の挙動を移植する

**先に、付録の数式原文で3つを確定させる**（`allocation-sql-skeleton.md` §0）。
配賦元の総額の出所／既配賦として引く項目の一覧／分母の母集合条件。
協和ではこの3つが揃ってズレたまま動くSQLが書けてしまい、検算でも1つしか捕まらなかった。

そのうえで、製品側が踏んだ落とし穴は、SQLでも同じように踏む。以下を必ず入れる。

**① 分母0でクエリを落とさない・行を消さない**

`NULLIF` で0除算を避け、比率は0として残す。行ごと消すと、その月が
「処理されなかった」のか「0%だった」のか後から分からなくなる。

```sql
COALESCE(numerator / NULLIF(denominator, 0), 0) AS ratio
```

**② 分母が0の月は配賦元を減算しない**

比率合計が0%の月に配賦元だけ減らすと、金額が消える。
減算する側の CTE で「その月の比率合計 > 0」を条件に入れる。

**③ 比率の分母を取り違えない**

分母は「配賦先“全体”の基準値合計」であって、1組織の値ではない。
`SUM(...) OVER (PARTITION BY 月)` のように、月ごとの合計で割る形にする。

**④ 段階配賦は順序をCTEで固定する**

前ステップの結果を次の配賦元に使う場合、その依存をCTEの並びで表す。
**同じ元金額を2つのステップが別々に配ると二重計上になる**ので、
「何を配り終えたか」を列で持って残余を計算する。

**⑤ 残余は必ず検算する**

`配賦元合計 = 配賦先合計（+ 残した配賦元）` が成り立つことを、月ごとに確認するクエリを
SQLと一緒に出す。合計保存が崩れていたら、③か④のどちらかが壊れている。

骨格そのものは `allocation-sql-skeleton.md`、検算の型は `reconciliation.md`。

## 6. ターン1で報告すること

レポートに按分・配賦の工程があったら、**各工程について軸を判定して表で出す。**
どちらで実装するかはユーザーの判断（組織マスタへの登録は業務側の影響が出るため）。

```
■ 按分工程の判定
  STEP2 担当者人件費 → 得意先   軸=得意先 → SQL（組織マスタに無い）
  STEP3 プロ本部経費 → 得意先   軸=得意先 → SQL
  STEP4 拠点販管費の残余 → 得意先 軸=得意先 → SQL ※「残余」は配賦機能に相当概念なし
  STEP1 売上・粗利の付与        按分ではない（単なる結合）
```
