# 配賦型SQLの骨格

配賦（按分）をSQLで書くときの構造。**`channel-aggregation.md`（統合型）とは別の類型**で、
UNION ALL で横に並べるのではなく、CTE を縦に積んで金額を移し替える。

判断（機能でやるかSQLで書くか）は `allocation.md`。ここは「SQLで書く」と決まった後の話。

## 0. 書き始める前に、付録の数式で確定させる3つ

協和の当初SQLは動いて数字も出たが、**この3つが全部ズレていた。**
当時は原本 Excel の数式を直接読んで発覚した（レポートの要約では検出できなかった）。
**今は原本を見られない前提なので、レポート付録の数式原文が唯一の根拠。**

| # | 確定させるもの | 協和で起きたズレ |
|---|---|---|
| 1 | **配賦元の総額の出所** | 予算対比表の科目 `ZDA` を使っていた。正しくは ⑥拠点別経費の `★販管費合計` |
| 2 | **既配賦として引く項目の一覧** | 4項目のうち SPD経費合計が抜けていた → 残余が過大 |
| 3 | **分母の母集合条件** | 売上が負の得意先も分母に入れていた。正しくは `L>0` のみ |

いずれも**エラーにならず、それらしい数字が出る。** 検算で気づけるのは1だけで、
2と3は「なんとなく合わない」形でしか現れない。

**先に §0 を潰してから §1 を書く。** 付録に該当の数式が無いなら、
その項目を「不明」と書いたうえで**配賦SQL全体を暫定扱いだと明記する**。
3つを質問としてユーザーに丸投げしない（原本を見ないかぎり答えられない）。
埋めにいくなら、配賦後のあるべき金額をもらって逆算する
（`report-input.md` §5-3 の (c)、`allocation.md` §6）。

## 1. 5段の骨格

```sql
WITH src AS (
    -- ① 配賦元：月 × 配賦元キー × 金額
),
basis AS (
    -- ② 基準値：月 × 配賦元キー × 配賦先キー × 基準値
),
ratio AS (
    -- ③ 比率：基準値 ÷ その月・その配賦元の基準値合計
),
alloc AS (
    -- ④ 配分：配賦元金額 × 比率
),
residual AS (
    -- ⑤ 残余：元の総額 − 既に配り終えた分   ※残余の工程がある場合のみ
)
SELECT ...
```

段を飛ばさない。特に②と③を1つのCTEにまとめると、分母の取り違え（§2）に気づけなくなる。

## 2. ③比率 — ここが事故の中心

分母は「**その月・その配賦元における、配賦先全体の基準値合計**」。
1レコードの値でも、全期間の合計でもない。ウィンドウ関数で書くのが安全。

```sql
ratio AS (
    SELECT
        month,
        src_key,
        dst_key,
        basis_value,
        SUM(basis_value) OVER (PARTITION BY month, src_key) AS basis_total,
        COALESCE(
            basis_value / NULLIF(SUM(basis_value) OVER (PARTITION BY month, src_key), 0),
            0
        ) AS ratio
    FROM basis
)
```

`PARTITION BY` に何を入れるかが仕様そのもの。協和 STEP2 なら
「担当者個人の、その月の総訪問数」が分母なので `PARTITION BY month, 社員番号`。
**月を入れ忘れると全期間合計で割ることになり、比率が桁違いに小さくなる。**

`NULLIF` + `COALESCE(..., 0)` は必須。基準値が全部0の月は実運用で普通に起きる
（期中に取引先が増えた、その月のデータが欠損）。製品側もエラー扱いをやめて
比率0%として扱う仕様に変えている（`allocation.md` §3）。

**行を消さない。** `WHERE basis_total > 0` で弾くと、その月が
「計算していない」のか「0%だった」のかが後から追えなくなる。比率0で残す。

### 2-1. 分子・分母・`PARTITION BY` のキーは同じ出所から取る

`PARTITION BY` に使うキー（拠点コードなど）が、分子側と分母側で**別のソース由来**だと、
構成比の合計が 100% にならない。エラーは出ない。

協和で実際にあった不具合: 分子（得意先の売上）はマスタ由来の拠点コードで、
分母（拠点内売上合計）はプロ経費由来の拠点コードだった。両者が食い違う得意先の分だけ
構成比が壊れる。**キーの付与は1つのCTEで1回だけ行い、以降はその列を使い回す。**

```sql
-- OK: 拠点コードの付与は customer_branch_map の1か所だけ
sales_with_ratio AS (
    SELECT
        p.cust, m.branch_cd, p.sales,
        SUM(p.sales) OVER (PARTITION BY m.branch_cd) AS branch_sales_total,
        DIV0(p.sales, SUM(p.sales) OVER (PARTITION BY m.branch_cd)) AS ratio
    FROM pro_measure p
    LEFT JOIN customer_branch_map m ON p.cust = m.cust   -- ← 分子も分母もこの m を見る
)
```

キーの出所が複数あって選ばざるをえないときは、先に突合表で件数を出す
（`cleansing-recipes.md` §4-3）。

### 2-2. 分母の**母集合条件**は数式原文にしか書かれていない

「誰を分母に入れるか」は比率の定義そのものなのに、レポートの `03 ロジックの確認` からは落ちる。
**付録の `SUMIFS` の条件原文をそのまま読む。** 付録に無ければ「不明」とし、暫定であると明記する。

```
AA = IF(L>0, L / SUMIFS(L:L, B:B, B, L:L, ">0"), 0)
                                      ~~~~~~~ ← 売上が正の得意先だけが分母
```

協和の当初SQLはここを見落とし、**売上が負の得意先も分母に入れていた。**
比率が全件わずかにズレるので、検算では「全月で一定割合ずれる」形で出る（`reconciliation.md` §1）。

```sql
-- 母集合条件は WHERE ではなく式の中で表す。行は残す
DIV0(
    CASE WHEN sales > 0 THEN sales ELSE 0 END,
    SUM(CASE WHEN sales > 0 THEN sales ELSE 0 END) OVER (PARTITION BY branch_cd)
) AS ratio
```

`WHERE sales > 0` で弾かない。**弾くとその得意先が出力から消える**（配賦額0で残るのが正）。

## 3. ⑤残余 — 二重計上を止める

「販管費合計 − 既に配賦した分 = 残余」を配る工程。ここが一番壊れやすい。

```sql
allocated AS (
    -- 先行ステップで配り終えた金額を、残余の単位（拠点など）で集計
    SELECT month, base_key, SUM(amount) AS allocated_amount
    FROM alloc_step2_and_3
    GROUP BY 1, 2
),
residual AS (
    SELECT
        t.month,
        t.base_key,
        t.total_sga - COALESCE(a.allocated_amount, 0) AS residual_amount
    FROM total_sga t
    LEFT JOIN allocated a USING (month, base_key)
)
```

守ること:

- **駆動表は「総額側」。** `FROM total_sga` を左に置き、配賦実績を `LEFT JOIN` する。
  逆にすると、**実績に1件も出てこない部門は行ごと消え、残余が丸ごと欠落する。**
  協和の当初SQLがこれで、3実績のどこにも登場しない部門の販管費が静かに消えていた
- **何を引くのかを列で持つ。** 「STEP2とSTEP3の合計を引く」なら、その2つだけを集めたCTEを
  明示的に作る。`alloc` 全体を引くと自分自身も引いてしまう
- **引く項目の一覧は付録の数式原文から取る。** 協和の当初SQLは既配賦 `Z` から SPD経費合計（`S`）が
  抜けていて、残余が過大になっていた。正しくは `Z = SUMIFS(S)+SUMIFS(T)+SUMIFS(U)+SUMIFS(X)` で、
  **4項目ある**。項目の数え漏れは検算に出にくい（金額が合わないだけで構造は壊れない）ので、
  数式の項を1つずつ突き合わせる
- **総額側が「配賦済みの表」でないか確認する。** 出す側マイナス・受ける側プラスで
  合計が0になる表がある。引き算に使うのはどちらの側かを決める（`reconciliation.md` §6-2）
- **`LEFT JOIN` + `COALESCE(..., 0)`。** 配賦実績が無い拠点は行ごと消える。
  `INNER JOIN` にすると、その拠点の残余が丸ごと消える
- **残余がマイナスになったら止める。** 既配賦が総額を超えている＝どこかで二重計上している。
  0 に丸めて隠さない。検算クエリで件数を出す（`reconciliation.md`）
- **プラスのまま残る残余は異常とは限らない**（配賦先が1件も無い本部部門など）。
  内訳を出して正常・異常を判定してから報告する（`reconciliation.md` §2）

## 4. 端数

比率を掛けた時点で小数が出る。**丸めるかどうかを先に決める。**

| 方針 | 使いどころ |
|---|---|
| **丸めない**（推奨） | 中間CTEでは丸めず、最終出力だけ丸める。合計のズレが最小 |
| 各行で丸める | 帳票と1円単位で合わせる必要があるときだけ |

各行で丸めると **配分額の合計 ≠ 配賦元金額** になる。1円単位で合わせるなら、
差額を最大行に寄せる（最終行に寄せると金額の小さい行に不自然な数字が出る）。

```sql
-- 差額寄せの考え方：月×配賦元ごとに、比率最大の1行へ端数を加える
ROW_NUMBER() OVER (PARTITION BY month, src_key ORDER BY ratio DESC) AS rn
```

協和の実測では、原本Excelとの差が売上で2円・粗利で5円あった。
**この程度の差は丸め由来なので合格。桁が違う差だけを追う。**

## 5. 多段階の順序

段階配賦は CTE の並びで順序を表す。**同じ元金額を2つの段階が別々に配ると二重計上。**

```
STEP2  担当者人件費   → 得意先   （訪問数比）
STEP3  本部経費       → 得意先   （粗利構成比）
STEP4  拠点販管費の残余 → 得意先  （売上構成比）← STEP2/3 の結果に依存
```

STEP4 の残余は STEP2・STEP3 の結果を引くので、その2つが確定してからでないと書けない。
**依存があるものは後ろに置き、依存元のCTE名を残余の計算式に直接書く**
（変数のように使い回さない。どこから引いたか読めなくなる）。

## 6. 出力の形

配賦結果は**元の明細に列として足す**か、**別テーブルとして持つ**かのどちらか。
レポート側が「得意先1行＝1レコード」を期待しているなら前者。

```
得意先CD / 得意先名 / 売上 / 粗利 / SPD管理料 / AMEX手数料
        / 按分_人件費 / 按分_本部経費 / 按分_拠点経費 / 営業利益
```

**按分結果は工程ごとに別列で持つ。** 合算して1列にすると、
どの工程が効いているか分からず、検算も切り分けもできなくなる。

## 7. 実装済みのものを上書きしない

協和では STEP2 が既に SQLジョブとして存在していた。

```
得意先毎に訪問数を比率として人件費を按分  (DC_SQL_JOB_0026)
  月 / 社員番号 / 本名氏名 / 顧客No / 集計得意先コード
  / 訪問数 / 人件費_合計 / 社員別訪問数合計 / 按分比率 / 得意先_エリア人件費
```

`社員別訪問数合計` が §2 の分母、`按分比率` が比率、`得意先_エリア人件費` が結果。
**クエリ147のアセット一覧に加工/SQLジョブが出るので、書き始める前に必ず見る。**
既にあるものを作り直すと、値が微妙に違う2系統ができて原因追跡が不可能になる。
